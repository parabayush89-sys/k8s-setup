Kubernetes Cluster Setup

A simple, step-by-step guide to building a three-node Kubernetes cluster using kubeadm and containerd.

Beginner friendly3 virtual machinesControl plane + 2 workersCommand reference

Notebook index & overview

In this lab, we prepare three CentOS 9 virtual machines, install the Kubernetes tools, create the control plane, connect worker nodes, and deploy a test Nginx application.

What are we building?A Kubernetes cluster is a group of machines that work together. The control plane manages the cluster, while worker nodes run applications inside Pods.

VM requirements

Create these three virtual machines. All machines must be on the same network and able to communicate using hostnames and IP addresses.

VM nameRoleOperating systemRAMCPUPurpose
k8s-masterControl planeCentOS 94 GB2 coresAPI server, etcd, scheduler and controller manager
k8s-worker1Worker nodeCentOS 94 GB2 coresRuns application workloads

Before you beginReplace every sample IP address with the real IP address of your VM. Keep a note of the master IP address and the join command generated later.

1. Prepare all nodes

RUN ON: MASTER + WORKER 1 + WORKER 2

Prepare the operating system on all three machines before installing Kubernetes.

1.1 Set hostnames

Each machine needs a unique name. Run the matching command on the matching VM.

Master node · Bash
sudo hostnamectl set-hostname k8s-master
Worker 1 · Bash
sudo hostnamectl set-hostname k8s-worker1
Worker 2 · Bash
sudo hostnamectl set-hostname k8s-worker2

1.2 Configure host resolution

Edit the hosts file on all nodes. Add the same three lines, using your actual VM IP addresses.

Bash · all nodes
sudo vi /etc/hosts
Example entries · replace sample IPs
192.168.x.x k8s-master
192.168.x.x k8s-worker1
192.168.x.x k8s-worker2

1.3 Disable swap

Why is this needed?In this training setup, kubelet expects to manage node memory. Swap can interfere with Kubernetes resource management.
Bash · all nodes
# Disable swap immediately
sudo swapoff -a

# Comment out the swap entry in /etc/fstab
sudo sed -i '/ swap / s/^\\(.*\\)$/#\\1/g' /etc/fstab

1.4 Set SELinux to permissive

Simple explanationPermissive mode logs SELinux policy violations instead of enforcing them. This is the setting used by the supplied lab procedure.
Bash · all nodes
# Change mode now
sudo setenforce 0

# Make the setting persistent
sudo sed -i 's/^SELINUX=enforcing$/SELINUX=permissive/' /etc/selinux/config

1.5 Firewall setting for this lab

Lab-only security noteThe original procedure disables firewalld to avoid port-related lab issues. This reduces host protection. Do not use this shortcut on an internet-facing or production machine; production systems should have only the required Kubernetes ports allowed.
Bash · all nodes
sudo systemctl disable --now firewalld

1.6 Load kernel modules

overlay supports the container filesystem. br_netfilter helps bridged network traffic pass through the packet-filtering rules.

Bash · all nodes
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

sudo modprobe overlay
sudo modprobe br_netfilter

1.7 Configure kernel networking

These settings enable IPv4 forwarding and allow bridged traffic to be processed by iptables.

Bash · all nodes
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF

# Apply settings now
sudo sysctl --system

1.8 Install and configure containerd

containerd is the container runtime. It downloads and runs containers for Kubernetes. The systemd cgroup setting keeps the runtime and Kubernetes using the same resource-management driver.

Bash · all nodes
# Add the Docker repository
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo

# Install containerd
sudo dnf install -y containerd.io

# Create the default configuration
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml >/dev/null

# Use the systemd cgroup driver
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/g' /etc/containerd/config.toml

# Enable and start containerd
sudo systemctl enable --now containerd
CheckpointAt this point, all three machines should have unique hostnames, node-to-node host entries, the required kernel settings, and containerd installed and running.

2. Install Kubernetes components

RUN ON: ALL THREE NODES

Install these three Kubernetes command-line components:

ComponentSimple meaning
kubeadmCreates and joins the Kubernetes cluster.
kubeletRuns on each node and manages Pods.
kubectlLets an administrator communicate with the cluster.

2.1 Add the Kubernetes repository

Bash · all nodes
cat <<EOF | sudo tee /etc/yum.repos.d/kubernetes.repo
[kubernetes]
name=Kubernetes
baseurl=https://pkgs.k8s.io/core:/stable:/v1.30/rpm/
enabled=1
gpgcheck=1
gpgkey=https://pkgs.k8s.io/core:/stable:/v1.30/rpm/repodata/repomd.xml.key
EOF

2.2 Install the packages

Bash · all nodes
sudo dnf install -y kubelet kubeadm kubectl --disableexcludes=kubernetes

# Enable kubelet; kubeadm will start it during setup
sudo systemctl enable kubelet
Version noteThe supplied transcript uses the Kubernetes v1.30 package repository and Calico v3.27.3 manifest. These are the versions recorded in this notebook; check compatibility and current support before using this as a fresh production installation guide.

3. Master node setup

RUN ON: MASTER ONLY

Now create the Kubernetes control plane. It includes the API server, etcd database, scheduler and controller manager.

3.1 Initialize the cluster

Bash · master node
sudo kubeadm init --pod-network-cidr=192.168.0.0/16
What does the option mean?--pod-network-cidr defines the IP address range used by Pods. This transcript uses 192.168.0.0/16 for the Calico setup that follows.

At the end, kubeadm prints a kubeadm join command. Copy the complete command and save it. You will run it on both worker nodes in Step 5.

3.2 Configure kubectl for your user

The kubeconfig file tells kubectl which API server to contact and how to authenticate.

Bash · master node
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

3.3 Check the control plane node

Bash · master node
kubectl get nodes
Expected at this stageThe master node may show NotReady. This is expected before a Pod network plugin is installed.

4. Install the Pod network (CNI)

RUN ON: MASTER ONLY

Kubernetes needs a Container Network Interface (CNI) plugin to provide Pod networking. This lab uses Calico.

4.1 Deploy Calico

Bash · master node
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.27.3/manifests/calico.yaml

4.2 Verify the network

Bash · master node
kubectl get pods -n kube-system
kubectl get nodes

Calico Pods should start. Wait a few minutes and check again. The master should become Ready when the network setup is healthy.

5. Worker node setup

RUN ON: WORKER 1 + WORKER 2

Join each worker to the control plane using the command printed by kubeadm init in Step 3.1.

5.1 Join the cluster

Bash · run separately on both workers
sudo kubeadm join <master-ip>:6443 --token <token> \\
  --discovery-token-ca-cert-hash sha256:<hash>
Important: use your real join commandThe placeholders <master-ip>, <token> and <hash> are examples, not literal values. Paste the full command generated by your master node.
  • Token: proves that the joining node is authorized to join.
  • Discovery hash: helps the worker verify the cluster certificate authority.

The transcript notes that join tokens expire after 24 hours. If needed, generate a fresh join command on the master:

Bash · master node
kubeadm token create --print-join-command

6. Verify the complete cluster

RUN ON: MASTER ONLY

After both workers have joined, check the node list and system Pods.

6.1 Check nodes

Bash · master node
kubectl get nodes

Expected result: the master and both worker nodes appear in the list with status Ready.

6.2 Check system Pods

Bash · master node
kubectl get pods -n kube-system -o wide

Look for the core Kubernetes components, CoreDNS and Calico Pods. They should reach the Running state.

7. Test deployment

RUN ON: MASTER ONLY

Deploy a simple Nginx web server to confirm that Kubernetes can run an application.

7.1 Create an Nginx deployment

Bash · master node
kubectl create deployment nginx-test --image=nginx:latest

This command asks Kubernetes to create a Deployment that runs an Nginx container in a Pod.

7.2 Expose the deployment

Bash · master node
kubectl expose deployment nginx-test --port=80 --type=NodePort

A NodePort Service makes the application reachable through a port on each node. Kubernetes normally selects a port in the 30000–32767 range.

7.3 Find the NodePort

Bash · master node
kubectl get svc nginx-test

In the PORT(S) column, you may see a value similar to 80:31456/TCP. In this example, 31456 is the NodePort. Your assigned port may be different.

7.4 Test from a worker

Bash · from a machine that can reach the worker
curl http://<worker1-ip>:31456
Success looks like thisIf Nginx is working and the network path is available, curl should return the Nginx welcome page HTML.

8. Stop and restart the Kubernetes cluster

VMWARE LAB · SAVE YOUR CLUSTER FOR LATER

Use this procedure when you want to shut down your VMware lab VMs and continue your Kubernetes practice later without rebuilding the cluster.

8.1 Before stopping the cluster

RUN ON: MASTER NODE

Check the current state of the cluster before shutting down the virtual machines.

Bash · master node
kubectl get nodes
kubectl get pods -A

For planned maintenance of an individual worker, you can first move workloads away from it:

Bash · master node · optional maintenance step
kubectl drain k8s-worker1 --ignore-daemonsets --delete-emptydir-data
When is drain needed?Repeat with the correct worker name if required. Draining is optional when you are simply shutting down the entire lab. It is useful when maintaining one node while the rest of the cluster stays online.

8.2 Shut down the nodes

For a complete lab shutdown, shut down the worker nodes first, then the master node.

RUN ON: EACH WORKER NODE
Bash · worker 1 and worker 2
sudo systemctl stop kubelet
sudo shutdown -h now

After both workers have shut down, run these commands on the master:

RUN ON: MASTER NODE · AFTER WORKERS ARE OFF
Bash · master node
sudo systemctl stop kubelet
sudo shutdown -h now

You can also shut down the VMs through VMware after the guest operating systems have shut down.

Important — preserve your cluster
  • Do not run kubeadm reset just to stop the cluster. It removes local Kubernetes configuration and is intended for dismantling or rebuilding a node.
  • Do not delete /etc/kubernetes, /var/lib/etcd, or the CNI configuration when you want to preserve the cluster.
  • Keep the VM disks and network configuration unchanged so the nodes retain their identities and IP addresses.

8.3 Start the cluster again

Start the VMs in this order:

  1. Start the master VM first.
  2. Wait for the master operating system to boot and its network to become available.
  3. Start worker1 and worker2.

On the master and both worker nodes, make sure containerd and kubelet are running:

Bash · all three nodes
sudo systemctl start containerd
sudo systemctl start kubelet

To make sure these services start automatically after future OS boots, check that they are enabled:

Bash · all three nodes
sudo systemctl enable containerd
sudo systemctl enable kubelet

On the master, check the cluster:

Bash · master node
kubectl get nodes
kubectl get pods -A

Give the services and Calico networking a little time to recover. Nodes may briefly show NotReady while components start. Check again:

Bash · master node
kubectl get nodes
kubectl get pods -n kube-system -o wide
Expected resultThe master and workers should return to Ready, and system Pods should become Running or reach their expected status.

8.4 When should you run kubeadm init again?

Normally, you do not run kubeadm init again when restarting a stopped cluster.Run kubeadm init on the master only when creating a new control plane — for example, during the first cluster setup, after intentionally resetting/dismantling the master, or when creating a fresh master VM. Do not run it just because you shut down or rebooted the master. The existing control-plane configuration and etcd data should be reused.

8.5 When should you run kubeadm join again?

Normally, you do not run kubeadm join every time a worker VM starts.Run kubeadm join on a worker only when adding it for the first time, after running kubeadm reset on that worker, or after rebuilding/removing and re-adding the worker VM. A normal reboot or shutdown/start cycle does not require a new join command.

If you need a new join command, generate one on the master:

Bash · master node
sudo kubeadm token create --print-join-command

Then run the generated command on the worker that needs to join.

Final lab checklist

Tick these items as you complete the practical.

  • Three CentOS 9 VMs created with the required resources.
  • All three nodes can communicate using their hostnames.
  • Swap disabled and required kernel settings applied.
  • containerd installed and started on all nodes.
  • kubeadm, kubelet and kubectl installed on all nodes.
  • Control plane initialized successfully.
  • Calico network Pods are running.
  • Both worker nodes joined the cluster.
  • All three nodes show Ready.
  • Nginx Deployment and NodePort Service created.
  • Nginx responds to the curl test.
